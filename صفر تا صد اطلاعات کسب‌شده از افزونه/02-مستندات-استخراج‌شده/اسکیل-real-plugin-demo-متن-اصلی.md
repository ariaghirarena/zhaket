# راهنمای ساخت دموی واقعیِ رابط افزونه برای صفحهٔ معرفی

این راهنما برای یک عامل هوش مصنوعی است که باید از یک افزونهٔ WordPress، صفحهٔ معرفی و دموی مرورگری بسازد؛ هدف این است که رابط واقعاً همان رابط افزونه باشد، نه تصویر ساختگی یا بازطراحیِ مشابه. قبل از شروع، تفاوت «رابط واقعی» و «نصب واقعی افزونه» را شفاف کنید.

## نکتهٔ صداقت: در این پروژه چه چیزی واقعاً انجام شد؟

در این پروژه **افزونه داخل یک WordPress قابل اجرا نصب نشد**. چیزی که واقعاً ساخته شد، دموی استاتیکی از **دارایی‌های واقعی پنل مدیریت افزونه** است: فایل‌های CSS و JavaScript رابط از خود افزونه برداشته شدند، در یک صفحهٔ HTML بارگذاری شدند، و درخواست‌های REST یا AJAX با دادهٔ نمونه در همان مرورگر پاسخ داده شدند. بنابراین:

- رابط و رندر صفحه‌ها از فایل‌های خود افزونه است؛ بازطراحی یا اسکرین‌شاتِ چسبانده‌شده نیست.
- سرور WordPress، پایگاه‌داده، PHP، ورود مدیر، REST API واقعی یا اجرای کدهای سمت سرور در دمو حضور ندارند.
- داده‌های فروشگاه، آمار و پاسخ‌های هوش مصنوعی نمونه و ساختگی‌اند. تغییرات در یک سایت واقعی ذخیره یا اجرا نمی‌شوند.
- هنگام انتشار باید این محدودیت‌ها جلوی چشم کاربر گفته شوند؛ دمو را «نسخهٔ نصب‌شده و متصل به فروشگاه واقعی» معرفی نکنید.

اگر الزام این است که **خود افزونه در WordPress واقعی اجرا شود**، از مسیر جایگزینِ «نصب روی staging» در انتهای سند استفاده کنید. هرگز افزونه را روی سایت عمومی یا محیطی با اطلاعات واقعی، بدون مجوز و پشتیبان‌گیری نصب/فعال نکنید.

## الگوی پیاده‌سازی الف: افزونه‌های SPA با REST API (نمونهٔ مرجع: Seolity)

### اجزای واقعی موجود در مخزن

- `seolity/`: سورس افزونهٔ WordPress.
- `seolity/assets/admin/`: دارایی‌های واقعی رابط پنل (CSS و JavaScript بدون مرحلهٔ build).
- `site/demo/index.html`: پوستهٔ دمو؛ ترتیب بارگذاری وابستگی‌ها در این فایل مهم است.
- `site/demo/config.js`: تنظیمات runtime مانند مسیر REST و اطلاعات نمایشی سایت.
- `site/demo/i18n-fa.js`: رشته‌های ترجمهٔ رابط فارسی.
- `site/demo/mock-data.js` و `settings-data.js`: داده و تنظیمات نمایشی.
- `site/demo/mock-api.js` و `mock-routes-*.js`: رهگیر Fetch و پاسخ‌های محلیِ endpointها.
- `site/demo/demo.css`: فقط سازگاری پوستهٔ استاتیک، فاصلهٔ نوار هشدار و رابط اصلی را تنظیم می‌کند.
- `site/assets/shots/`: تصاویر گرفته‌شده از مرورگر واقعی برای معرفی قابلیت‌ها.

### ترفند فنی اصلی: پاسخ‌دادن به API قبل از راه‌اندازی UI

پنل افزونه یک SPA است که از جاوااسکریپت، REST API را صدا می‌زند. به‌جای ساختن رابط مشابه، HTML ابتدا فایل‌های ترجمه، config، دادهٔ نمونه و interceptor مربوط به `fetch` را بارگذاری می‌کند؛ سپس فایل‌های اصلی رابط افزونه اجرا می‌شوند. interceptor درخواست‌های UI را می‌گیرد و پاسخ‌های مناسب را از حافظه می‌دهد. در این نمونه، مسیر API نمایشی `__seolity_demo_api__` است و هیچ سروری در این مسیر وجود ندارد.

ترتیب بارگذاری در `site/demo/index.html` را حفظ کنید:

1. ترجمه، config، دادهٔ پایه و تنظیمات نمونه؛
2. `mock-api.js` و همهٔ `mock-routes-*.js`؛
3. دارایی‌های اصلی افزونه، به‌ترتیب وابستگی‌ها (`charts.js`, `ui.js`, `app.js`, سپس `pages-*.js`).

اگر mock بعد از `app.js` بارگذاری شود، ممکن است درخواست اولیه زودتر به شبکه برود یا شکست بخورد. اگر فایل‌های اصلی UI ویرایش نشوند، fidelity رابط با افزونه حفظ می‌شود؛ تغییرات مخصوص دمو را در HTML/CSS/mockها نگه دارید.

## الگوی پیاده‌سازی ب: افزونه‌های PHP View + jQuery AJAX (نمونهٔ مرجع: ARIAGH.AIWRITER)

بسیاری از افزونه‌های وردپرسی به‌جای SPA کامل، تب‌های پنل مدیریت را با قالب‌های PHP (`admin/views/*.php`) رندر می‌کنند و تمام تعامل‌ها را از طریق یک فایل اصلی `assets/js/admin.js` (مبتنی بر `jQuery` / `admin-ajax.php`) و `assets/css/admin.css` انجام می‌دهند. در این حالت هم **هرگز رابط را دستی بازطراحی نکنید**؛ بلکه:

1. **کپی فایل‌های دست‌نخوردهٔ افزونه:** `assets/css/admin.css` و `assets/js/admin.js` و SVGهای لوگو را بدون هیچ تغییری در `demo/plugin/assets/` کپی کنید و کتابخانه‌های موردنیاز (مثل `jquery.min.js` و `jquery-ui.min.js`) را به‌صورت خودمیزبان در `demo/vendor/` بگذارید تا دمو کاملاً آفلاین روی cPanel هم کار کند.
2. **رندر واقعی تمام قالب‌های PHP در زمان ساخت (`build_real_demo.php`):**
   - با `php-cli` یک شیم حداقلی WordPress (`get_option`, `wpdb`, `esc_*`, `wp_date`, `number_format_i18n`, `admin_url`, `get_categories`, ...) بسازید، کلاس‌های واقعی خود افزونه را `require_once` کنید و با دادهٔ نمونهٔ ایمن (مثل `demo-coffee.ir`، بدون هیچ کلید یا دادهٔ واقعی) متد `render()` را برای تک‌تک تب‌ها اجرا کنید.
   - خروجی HTML واقعی همهٔ تب‌ها و شیء `wp_localize_script` (مثل `window.AAW`) را در یک فایل `demo/views-bundle.js` ذخیره کنید. (در صورت وجود قانون «عدم نمایش شماره نسخه»، فقط رشتهٔ نسخه را در خروجی رندر فیلتر کنید.)
   - لینک‌های `admin.php?page=...&tab=X` را در `admin_url()` به `?tab=X` نگاشت کنید تا جابه‌جایی بین تب‌ها در دمو بی‌نقص کار کند.
3. **ترتیب بارگذاری در `demo/index.html`:**
   1. `vendor/jquery.min.js` و `vendor/jquery-ui.min.js`؛
   2. `views-bundle.js`؛
   3. اسکریپت همگام (synchronous) که `?tab=` (یا `#hash`) را می‌خواند، HTML واقعی همان تب را در DOM می‌گذارد و `window.AAW` را با `ajax: '__demo_ajax__'` مقداردهی می‌کند؛
   4. `mock-ajax.js` که `$.post('__demo_ajax__', ...)` و `window.fetch` را **قبل از اجرای `admin.js`** رهگیری می‌کند و با قرارداد دقیق کنترلر AJAX افزونه (`class-*-ajax.php`) و ذخیره‌سازی موقت در `sessionStorage` پاسخ می‌دهد (عملیات حساس/سروری پیام شفاف «در دموی مرورگری غیرفعال است» برمی‌گردانند)؛
   5. فایل دست‌نخوردهٔ `demo/plugin/assets/js/admin.js`.

## فرایند بازتولید برای یک افزونهٔ دیگر

### ۱) مجوز، منبع و محدوده را مشخص کن

- از کاربر مخزن/ZIP افزونه و اجازهٔ استفاده از فایل‌ها و تصویرهای آن را بگیر؛ برای مخزن عمومی هم مجوز را بررسی کن.
- نسخهٔ افزونه، تاریخ/commit منبع و مسیر فایل‌ها را ثبت کن. رازها، فایل‌های پیکربندیِ حاوی کلید، و دادهٔ مشتری را وارد مخزن عمومی نکن.
- تصمیم را مستند کن: دموی استاتیک با mock، یا WordPress واقعی در staging. این دو را با هم اشتباه نگیر.

### ۲) معماری افزونه و نقطهٔ ورود پنل را پیدا کن

- README و فایل اصلی PHP را بخوان؛ بررسی کن پنل در چه صفحه‌ای، با چه مجوزی و چه داده‌هایی راه‌اندازی می‌شود.
- مسیر دارایی‌های مدیر را پیدا کن. فایل‌های CSS/JS، ترجمه‌ها، فونت‌ها و لوگوها را فهرست کن؛ تشخیص بده کدام فایل‌ها build شده‌اند و کدام را می‌توان مستقیم اجرا کرد.
- همهٔ endpointهای مورد استفاده را از PHP router/controllerها و از جست‌وجوی `fetch`, `api`, `rest_url`, `wp.apiFetch`, `admin-ajax` در JS استخراج کن. برای هرکدام متد، URL، query/body و شکل پاسخ/خطا را یادداشت کن.
- هر صفحه را با کد رندرش تطبیق بده: چه فیلدهایی را بی‌قیدوشرط می‌خواند؟ enumها، timestampها، اعداد و آرایه‌ها چه شکلی‌اند؟ شکل دادهٔ mock باید با قرارداد UI بخواند، نه فقط شبیه چیزی باشد که در کارت دیده می‌شود.

### ۳) پوستهٔ مرورگری کمینه بساز

- یک `index.html` مستقل در مسیر دمو بساز؛ CSS/JS اصلی را با مسیر نسبی درست بارگذاری کن.
- تنظیمات لازمِ runtime را با مقدارهای غیرحساس و نمایشی فراهم کن؛ مسیر API و URL فروشگاه نمونه را واضح تنظیم کن.
- برای SPA یا پنلی که در WordPress به `wp-admin` یا نوار مدیریت تکیه دارد، فقط overrideهای لازم را در CSS مخصوص دمو اضافه کن. کلاس‌ها و فایل‌های اصلی رابط را بی‌دلیل دستکاری نکن.
- اگر افزونه به nonce، capability، WordPress globals یا توابع PHP وابسته است، ببین آیا می‌توان قرارداد frontend را امن و صادقانه mock کرد. اگر بدون backend واقعی نمی‌شود، تظاهر نکن: از محیط staging استفاده کن یا دامنهٔ دمو را محدود کن.

### ۴) API محلی را با قرارداد واقعی شبیه‌سازی کن

- `fetch` و/یا `jQuery.post` را پیش از شروع UI بگیر؛ فقط endpointهای مورد نیاز را پاسخ بده.
- route را با method + path + query/body تطبیق بده؛ handlerهای عام را بعد از خاص‌ها بگذار («اولین handler منطبق برنده است»، پس تکرار یک route می‌تواند mock درست را shadow کند).
- برای GETهای نامعلوم، دادهٔ خالیِ نوع‌درست برگردان (مثلاً فهرست خالی یا object لازم)، نه دادهٔ خیالیِ ناقص که صفحه را می‌شکند.
- برای POST/PUT/DELETE ناشناخته یا حساس، موفقیت جعلی برنگردان. پیام روشن «در دمو غیرفعال است» یا خطای مشخص بده. اگر یک عمل را mock می‌کنی، پیامدش را هم در UI منعکس کن؛ موفقیت ساختگیِ بدون تغییر وضعیت گمراه‌کننده است.
- اگر دادهٔ ساختگی، route یا خطا به کاربر نشان داده می‌شود، در نوار بالای دمو و/یا کنار عمل توضیح بده.
- هیچ درخواست یا داده‌ای را به سرویس خارجی/واقعی نفرست؛ مخصوصاً کلید API یا محتوای کاربر را در mock نگذار.

### ۵) دادهٔ نمایشی معنادار اما بی‌خطر بساز

- داده‌ها را بر اساس schema و rendererهای واقعی تولید کن؛ مقدارهای ضروری را کامل کن و نوع‌ها را رعایت کن.
- برای فروشگاه/مشتری، نام دامنهٔ رزروشده یا آشکارا نمونه (مثل `demo-shop.ir` یا `demo-coffee.ir`) و محتوا/نام غیرواقعی به‌کار ببر.
- اعداد سازگار باشند: اگر کارت تعداد محصول می‌گوید 120، جدول محصول هم باید داده‌ای باورپذیر داشته باشد. متن، تاریخ، امتیاز و وضعیت‌ها با هم تضاد نداشته باشند.
- در تمام تب‌ها دادهٔ کافی برای حالت خالی، جدول، نمودار و خطا بساز؛ فقط صفحهٔ اول را پر نکن.
- از اطلاعات واقعی داخل backup، log یا پایگاه‌داده برای دمو استفاده نکن، حتی اگر در فایل‌های ورودی پیدا شد.

### ۶) راه‌اندازی و آزمون را قبل از اسکرین‌شات انجام بده

نمونهٔ سرو استاتیک از ریشهٔ سایت:

```bash
cd site
python3 -m http.server 8765 --bind 0.0.0.0
```

باز کن: `http://127.0.0.1:8765/demo/` در محیط خودت. در پیش‌نمایش میزبانی‌شده، آدرس مرورگر باید همان preview host باشد؛ کد صفحه را طوری ننویس که در مرورگر کاربر به `localhost` یک سرویس دیگر درخواست بفرستد.

چک‌لیست:

- Console و Network را بررسی کن؛ خطای JS، 404 دارایی، درخواست خارجی ناخواسته و خطای API واقعی نباید پنهان بماند.
- همهٔ slugهای تب‌ها را یکی‌یکی در مرورگر واقعی (Playwright/Puppeteer Chromium) باز کن و خطاهای JS و HTTP را چک کن.
- ناوبری، back/forward، hash/query، جدول‌ها، نمودارها، tabهای داخلی، حالت خالی، toast، modal و responsive را بررسی کن.
- برای screenshot، صفحه را در Chromium واقعی باز کن؛ jsdom برای ظاهر، فونت، layout و Canvas کافی نیست.
- تصاویر را بعد از آخرین تغییر CSS دوباره بگیر؛ screenshot قدیمی ثابت نمی‌کند نسخهٔ تازه درست رندر می‌شود.
- مهم‌ترین تعامل‌های خطرناک را هم بزن و مطمئن شو چیزی به backend واقعی نمی‌رود.

## اسکرین‌شات: روش واقعیِ مرورگری

تصاویر رابط با Chromium headless (Playwright یا Puppeteer) گرفته می‌شوند، نه از mockup تصویری:

1. URL و slug، عرض/ارتفاع (مثلاً `1440×860` یا `1440×900`)، زمان انتظار و حالت تمام‌صفحه را برای هر عکس ثبت کن.
2. فونت محلی و تصویرهای شبکه‌ای را پیش از capture آماده کن؛ به سرویس فونت خارجی متکی نباش.
3. انیمیشن، cursor، focus outline ناخواسته، toast و skeleton را کنترل کن؛ ابتدا صبر کن داده و فونت واقعاً آماده شوند.
4. عکس را بازبینی کن: برش، overlap، متن بیرون‌زده، راست‌به‌چپ، کنتراست، لوگو، alertهای کنسول و محتوای ساختگی.
5. هم desktop (`1440px`) و هم حداقل یک عرض موبایل (`390px`) را بررسی کن؛ اسکرین‌شات desktop به معنی تأیید responsive نیست.
6. فایل‌ها را در مسیر مشخصی مثل `assets/shots/` بگذار و پس از هر تغییر مجدداً capture کن.

## افزودن به صفحهٔ معرفی و انتشار

- کنار هر screenshot نام قابلیت و توضیح واقعی‌اش را قرار بده؛ تصویر decorative را با کارکرد قابل تعامل اشتباه نکن.
- CTA دمو را به مسیر نسبی درست وصل کن (`./demo/index.html?tab=...` یا `./demo/#/...`) و با base path میزبانی آزمایش کن.
- هشدار «دموی زنده، دادهٔ نمونه، بدون تغییر روی سایت واقعی» را در خود دمو نگه دار، حتی اگر صفحهٔ معرفی هم توضیح داده باشد.
- از فایل‌های داخل پوشهٔ انتشار مطمئن شو: لینک CSS/JS و فونت‌ها باید بعد از deploy هم 200 باشند.

## اگر واقعاً باید افزونه در WordPress نصب شود

دموی استاتیک بالا، نصب واقعی نیست. برای نصب واقعی:

1. WordPress خالی و موقت را در staging/لوکال با نسخهٔ سازگار PHP و DB بساز؛ سایت را عمومی نکن و robots/indexing را ببند.
2. ZIP/پوشهٔ افزونهٔ مجاز را از **منبع واقعی** نصب کن؛ نسخه و checksum/commit را ثبت کن. قبل از فعال‌سازی، کد و نیازمندی‌ها را بررسی کن.
3. با حساب Administrator مخصوص تست وارد شو، افزونه را فعال کن، و onboarding/وابستگی‌ها را مطابق مستندات افزونه انجام بده. کلیدها را فقط اگر واقعاً ضروری‌اند در secret store محیط staging قرار بده، نه در کد frontend یا screenshot.
4. دادهٔ نمونهٔ مستقل بساز، backup بگیر، و دسترسی outbound/ایمیل/عملیات مخرب را محدود کن.
5. مرورگر را روی همان staging باز کن و screenshot مستقیم از UI بگیر. آدرس خصوصی، ایمیل، nonce، API key، مشتری واقعی و اطلاعات میزبان را قبل از انتشار حذف/پوشانده کن.
6. اگر باید دمو عمومی باشد، هر بازدیدکننده را به staging مشترک و قابل تغییر وصل نکن. محیط read-only/قابل reset، sandbox مجزا، نرخ‌دهی و کنترل سوءاستفاده در نظر بگیر؛ یا به دموی استاتیک با mock برگرد.
7. اسناد را صادقانه برچسب بزن: «WordPress واقعی در محیط آزمایشی» فقط وقتی واقعاً همان است؛ اگر backend mock است، «رابط واقعی با دادهٔ نمونه» بنویس.

- [ ] مشخص است که backend واقعی نصب/استفاده شده یا فقط frontend با mock اجرا می‌شود.
- [ ] مجوز و منشأ افزونه و تصاویر روشن است؛ secret و دادهٔ شخصی در خروجی نیست.

- [ ] schema پاسخ‌های mock با rendererهای اصلی سازگار است؛ خطاها و عمل‌های غیرفعال صادقانه‌اند.
- [ ] دارایی‌های اصلی UI از همان افزونه‌اند و تفاوت‌های demo جدا نگه داشته شده‌اند.
- [ ] Console/Network و desktop/mobile آزموده شده‌اند.
- [ ] screenshotها از مرورگر رندرشده‌اند و پس از آخرین تغییر بازبینی شده‌اند.
- [ ] صفحهٔ معرفی limitation دمو را واضح می‌گوید و CTA به URL درست می‌رود.
